# Veronica Phase 1G: Final Pre-Implementation Readiness Review

**Review type:** Read-only documentation and repository-state review
**Status:** Planning and documentation only
**Review date:** 2026-11-24
**Scope:** Phase 1A-1F planning records and the repository worktree state. No source implementation, tests, configuration, downloads, installations, benchmarks, or training were performed for this review.

## 1. Executive summary

**Verdict: NOT READY to begin native-model implementation or training.** The project has a documented direction and a useful provider-neutral integration boundary, but it does not yet have an approved dataset, a selected tokenizer or model configuration, a frozen evaluation set and baseline, approved pass/fail thresholds, or a verified ML runtime on the target hardware. The current planning matrix explicitly says data/model operations and implementation are not authorized.

The following high-level directions are confirmed in the reviewed records:

- The first tiny Veronica language model is intended to be trained from scratch.
- Veronica's eventual native final answers must be generated by its own model, not by Ollama or another pretrained AI model.
- English, Hindi (Devanagari), and Hinglish (Roman Hindi) have equal priority. Keep language-specific data inventories, evaluation, and quality reporting separate. Equal priority does not approve equal sampling percentages.
- The Phase 1A approval is limited to provider-neutral application and orchestration boundaries. It does not approve or implement a native model.

These are **directional decisions, not execution authorization**. Phase 1D records the data, licensing, privacy extensions, tokenizer, architecture, compute, dependencies, storage, evaluation, inference runtime, retrieval, network/API, and release decisions as pending or not authorized. Recommendations in Phase 1B, 1C, 1E, and 1F do not supersede that matrix.

The worktree was already dirty before this report was created: the status check showed modified application/test files and untracked provider, test, and documentation paths. This review did not inspect or alter those diffs. The latest Phase 1A approval therefore must not be assumed to cover unreviewed uncommitted changes.

## 3. Cross-phase consistency findings

### Consistent direction and boundaries

- Phase 1B-1F consistently describe a first from-scratch model as a small educational milestone, not a capable general assistant or a guaranteed Ollama replacement.
- The future native-answer requirement is distinct from inference-engine ownership. A third-party runtime might execute Veronica-trained weights, but that approach is still pending approval.
- The plans consistently separate the application/provider boundary from training, tokenizer, retrieval, memory, and deployment systems. The current provider boundary can be reused, but the native provider remains a scaffold.
- Phase 1C and 1D correctly distinguish dataset-card declarations from full underlying rights, privacy, attribution, and model-distribution clearance. No candidate source is approved.
- Phase 1C and 1D require split/leakage controls, including keeping final test examples out of tokenizer fitting as well as model training. Related templates, paraphrases, and duplicates must not cross splits; a small Hinglish set must not be reused for training and final evaluation.
- Phase 1C's proposed evaluation categories and Phase 1F's comparison criteria are planning recommendations. The numeric thresholds remain unapproved, as stated in Phase 1C and 1D.

### Chronology and documentation inconsistencies to retain as caveats

1. **Language priority:** Phase 1C §4 still says relative priority across English, Hindi-Devanagari, Hinglish-Roman, and technical/code is undecided. The later Phase 1D DEC-01 and Phase 1F §2 explicitly confirm equal priority for the three target languages. Treat the later decision as controlling; technical/code remains a separate format/task tag, not a fourth target language with confirmed equal priority. Phase 1C should be reconciled in a future documentation update, not silently interpreted as current approval for ratios.
2. **Hardware facts:** Phase 1B and Phase 1D describe some system facts as unknown because they had not been measured then. Phase 1E later records CPU, RAM, storage, GPU, driver, and Python observations. Use Phase 1E for the observed facts, while preserving Phase 1D's pending decision about laptop-only versus external compute/storage.
3. **Test evidence:** Phase 1B records a historical application-suite result of 356 collected, 355 passed, and 1 skipped (Windows symlink privilege). Phase 1C says it did not rerun tests. No tests were run for this Phase 1G review, so those results are not a current verification of the dirty worktree.
4. **Phase 1A status and current worktree:** earlier NEEDS FIXES reports precede the later approval. In addition, the current status check shows uncommitted changes to AI/provider-related code and tests. The approval audit applies to the reviewed state and scope; the present uncommitted state needs its own validation before relying on it.
5. **Illustrative examples:** Phase 1C's tokenizer/vocabulary examples and Phase 1F's 1M-25M parameter configurations are calculations or experiment candidates, not selections. Phase 1F's context length, vocabulary sizes, tied embeddings, and architecture counting assumptions do not establish approved design choices.

No contradiction changes the confirmed high-level direction. The inconsistencies above do affect how current approval and technical readiness should be represented.

## 5. Unresolved dependencies

### Data sources, rights, privacy, and retention

- Approve each exact source and revision for its specific purpose. Review underlying content, terms, attribution, privacy, permitted transformations, and intended checkpoint/output distribution; a dataset-card license label alone is insufficient.
- No source is approved. IndicCorpV2 paper and hosted-card/viewer statistics may describe different revisions or representations; exact revision and contents would need verification before any future use. CC0 does not resolve every underlying third-party rights or privacy question.
- Wikimedia's January 2027 sunset notice concerns specified legacy XML dump formats, not every data format. MediaWiki Content File Exports are the recommended replacement; source-specific licensing, attribution, and privacy review remain prerequisites.
- Define raw/normalized/tokenized data retention, access control, backups, deletion/revocation lineage, protected attribution records, and any legal review before collection.
- Keep personal conversations and SQLite memories outside training by default. Existing credential checks are not a comprehensive corpus privacy solution.

### Language data and split isolation

- Equal priority is confirmed, but the amount, quality, provenance, and independent availability of approved data in each language are unknown. No equal proportions or quotas are approved.
- Keep separate inventories and training/validation/sealed-test evaluation and quality reports for English, Hindi-Devanagari, and Hinglish-Roman. Technical/code can be tracked as a distinct format/task stratum.
- Establish source/document and duplicate-cluster splits. Related templates, paraphrases, revisions, translations, and duplicates belong in the same split.
- Exclude final-test examples from both model training and tokenizer fitting. Do not reuse the same small authored Hinglish collection for training and final evaluation.

### Tokenizer, architecture, objective, and optimizer

- SentencePiece BPE with byte fallback is a recommended candidate, not an approved implementation. No tokenizer or vocabulary is selected.
- Vocabulary cost depends on architecture and hidden width: 8,192 entries × 256 hidden dimensions equals 2,097,152 parameters for one embedding matrix; untied input/output matrices can increase the cost. Vocabulary must be decided only after architecture, hidden dimension, and total parameter budget are approved.
- A decoder-only causal Transformer is a reference candidate, not an approved model. Phase 1F's parameter configurations and memory calculations are illustrative, assume particular design/counting choices, and do not guarantee a fit on the GPU.
- Causal next-token prediction is a described training objective, not authorization or a complete training specification. Optimizer, precision, initialization, objective details, packing, batch/sequence length, and checkpoint policy remain open.

### Hardware, runtime, and dependencies

Phase 1E records these observations: Intel Core i5-13420H (8 cores/12 logical processors), 16 GB RAM, Windows 11 64-bit, RTX 3050 Laptop GPU with 6,144 MiB VRAM and compute capability 8.6, driver 576.93, driver-reported CUDA compatibility 12.9, Python 3.14.5, 281.95 GiB free on D: and 18.42 GiB on C:. The approximately 2.81 GiB free-RAM figure is a snapshot, not a stable training budget.

Important unknowns remain: sustained throughput and thermals; practical free VRAM/RAM under the target workload; storage performance and allocation; CUDA Toolkit/framework runtime; and actual execution of an exact ML release on this Windows/RTX 3050 combination. Phase 1E reports that PyTorch documentation lists Python 3.10-3.14, so 3.14.5 is within that documented range, but the exact release, CUDA wheel, driver/runtime combination, and RTX 3050 execution are unverified. No relevant ML framework was installed in the observed environment. Laptop-only compute versus external resources is still a user decision.

### Evaluation, integration, retrieval, and deployment

- Approve a frozen, language-separated evaluation set and baseline before setting numerical thresholds. Minimum language-specific performance, readability/coherence, repetition/incoherence, comprehension/reasoning, safety, privacy, unsupported factual claims, and failure/limitations reporting all need explicit approval.
- No native inference runtime or engine is selected. `VeronicaModelProvider` is documented as a nonfunctional scaffold; the application/provider boundary does not create model weights or answer generation.
- Existing SQLite memory is local personal memory with lexical matching, not a knowledge base, vector store, or training corpus. Document retrieval, source attribution, update/removal, and memory use with native generation remain unresolved.
- No API/server exists in the documented architecture. Offline guarantees, online search/TTS, network access, authentication, remote exposure, cloud deployment, and privacy boundaries require separate decisions and security review.

## 7. Critical blockers

1. **No operational authorization:** the current scope is planning/read-only; Phase 1D DEC-19 explicitly leaves data/model operations unauthorized.
2. **No approved data or rights package:** there is no source/revision approved for use, no completed licensing/privacy decision, and no retention/access policy.
3. **No approved evaluation basis:** there is no frozen baseline/test set or approved numerical gate. Without it, model selection or a claim of readiness cannot be justified.
4. **No selected or validated model stack:** tokenizer, vocabulary, architecture, parameter budget, optimizer, dependency set, and runtime are pending; exact GPU execution is unverified.
5. **Current worktree differs from the reviewed approval baseline:** uncommitted application/provider/test changes exist. Their behavior was not evaluated in this documentation review, so the Phase 1A approval cannot be generalized to them.

## 9. Recommended next steps

The sequence below is a **proposal for future separately authorized phases**, not permission to execute them:

1. **Confirm the working baseline and scope.** Review the actual uncommitted provider/application changes and establish which code snapshot, if any, is the approved foundation. Revalidate the provider contract and tests for that snapshot.
2. **Close governance decisions.** Approve or reject exact data sources/revisions, licensing and privacy review, attribution, retention, storage, access, and any consent process. Do not download or process data before the relevant approvals.
3. **Design evaluation before data/model work.** Approve language-separated evaluation inventories, source and duplicate-group split rules, sealed test access, scoring/rater process, and baseline. Approve all numerical acceptance thresholds separately; do not invent them before a set and baseline exist.
4. **Approve a data inventory and tokenizer experiment.** Only after source clearance, inventory eligible data independently for all three languages. Then approve tokenizer candidate, train-only fitting boundary, normalization, vocabulary/parameter budget, and artifact controls.
5. **Close architecture and resource decisions.** Select an architecture/parameter budget, objective/optimizer, precision, context, and laptop/external-resource scope using the approved data and evaluation constraints. Explicitly approve storage and runtime/dependency investigation.
6. **Validate compatibility in a bounded, isolated phase.** After authorization, verify the exact Python/framework/CUDA/driver/GPU combination and measure representative resource use before any model configuration is treated as feasible.
7. **Authorize a small from-scratch pilot only after all gates pass.** Bind the run to a versioned approved training split, tokenizer, configuration, and evaluation harness. Keep validation read-only for checkpoint selection and final test sealed until final evaluation.
8. **Evaluate before integration.** Report all per-language and task results, failed thresholds, uncertainty, limitations, and safety/privacy findings. Do not replace Ollama or switch provider defaults unless the user separately approves it after the release gates pass.
9. **Plan retrieval, memory, online/offline, and serving separately.** Keep personal memory, approved document evidence, web evidence, and training data distinct. Approve any API/network/cloud scope and security controls before implementation or exposure.
