# Veronica Phase 1B: Native AI Foundation Plan

**Status:** Architecture planning only

**Scope:** No implementation, package installation, model or dataset download, training, configuration change, or source/test change is authorized by this plan.

## Executive summary

Veronica has a useful provider-neutral application boundary, but it does not yet have a native language model, tokenizer, training pipeline, inference runtime, knowledge-retrieval system, or API server. Text answers are currently generated by Ollama. `VeronicaModelProvider` is an explicit, nonfunctional scaffold; it does not load model weights or generate answers.

The recommended direction is to build ownership incrementally and distinguish three separate goals:

1. **Own the model weights:** train a small model from scratch on approved, documented data. A temporarily used pretrained model can be a research comparison, but cannot be Veronica's permanent answer engine if the goal is independent answer generation.
2. **Own the tokenizer and training pipeline:** develop and version them with the model and its data provenance. A custom tokenizer is achievable on ordinary CPU resources, but does not itself make the model capable.
3. **Own the complete AI system:** also own the inference implementation, retrieval and memory policies, evaluation, deployment, and API. This is a much larger, multi-stage engineering goal.

The RTX 3050 Laptop GPU with 6 GB VRAM is suitable for small, bounded experiments and likely useful for constrained inference after measurement. It is not a realistic basis for training a powerful general-purpose LLM. A small model trained from scratch on this machine would be an educational and architectural milestone, not a capable replacement for today's hosted or open models. No useful-quality or performance threshold can be promised without benchmarks and a larger, approved data/compute budget.

**Recommendation:** begin with non-production learning experiments: define dataset and privacy rules, build repeatable evaluation, train a tokenizer, and measure a tiny from-scratch model. Keep the existing Ollama implementation unchanged and operational. Later, integrate a genuinely Veronica-trained checkpoint through the existing provider contract, initially using a lightweight inference runtime as an implementation detail. Treat a custom production inference engine and broad cloud/server deployment as later, separately approved goals.

### Existing assets and functionality limits

The repository includes a local Whisper `base` model (`data/models/whisper/base/model.bin`, about 145 MB) and two local Piper voice models (about 63 MB each). These are transcription and speech-synthesis assets; none is a text-generation model for Veronica.

Current persistent memory is explicit and local, with lexical matching rather than embeddings or semantic retrieval. Conversation history and teacher session state are bounded/in-process rather than a durable knowledge graph or full conversation archive. There is no first-party tokenizer, text-model checkpoint, dataset-curation pipeline, training/evaluation harness for language models, native inference engine, or server/API.

The repository's test suite currently passes its application tests (details in §8), but those tests do not establish native-model quality, training reproducibility, CUDA performance, or offline behavior for an unimplemented model.

## 2. Dependencies, configuration, and operating assumptions

`requirements.txt` currently declares `faster-whisper`, NumPy, Piper, sounddevice, PyAV, Edge TTS, and Pillow. It does **not** declare PyTorch, Transformers, Tokenizers, SentencePiece, PEFT, or a language-model training/runtime stack. No dependency is proposed for installation in this planning phase.

Verified example configuration has Ollama as the current text provider configuration, `VERONICA_AI_PROVIDER` support in source, web search disabled by default, and local paths for speech assets and SQLite memory. The Ollama adapter defaults to a loopback service; Ollama itself must be installed and running for current text generation. Optional Tavily web search needs Internet access and a Tavily key. Microsoft Edge Neural TTS is online; local Whisper and Piper paths are designed not to download models automatically.

The current active virtual environment reports Python 3.14.5. Adding an ML stack will require confirming, rather than assuming, compatible Windows/Python wheels, CUDA support, and runtime availability at implementation time. The existing Python version and passing tests do not certify compatibility of an uninstalled training or inference stack.

No values from a local `.env` were inspected. The repository's `.env.example` was used only to understand configuration names and defaults.

### Hardware facts and unknowns

For this plan, the confirmed hardware is Windows, an NVIDIA RTX 3050 Laptop GPU, and 6 GB VRAM. CPU model, system RAM, available disk, GPU driver/CUDA runtime, thermal/power limits, and sustained GPU performance are **not assumed**. Earlier audit notes about CPU/RAM are not treated as verified current capacity here. Confirm these before selecting batch sizes, sequence lengths, or a training/runtime stack.

Approximate parameter storage, not a fit guarantee:

| Weight representation | 1B parameters, raw weights only | 3B parameters, raw weights only |
|---|---:|---:|
| FP16/BF16 | ~2 GB | ~6 GB |
| INT8 | ~1 GB | ~3 GB |
| 4-bit | ~0.5 GB | ~1.5 GB |

Actual formats include metadata/scale overhead, and runtime memory also includes activations, temporary buffers, tokenizer/context state, and the KV cache. The GPU is also used by Windows/display workloads. Thus a 3B FP16 checkpoint already consumes approximately the entire VRAM before inference overhead; even a quantized checkpoint fitting on paper does not establish acceptable speed, context length, or stability. Training requires additional memory for gradients, optimizer state, and activations, so inference-sized estimates cannot be used to promise training fit.

First GPU work should be measurement-led: check that the runtime sees the intended GPU, record idle/peak VRAM and temperature, then run a small representative prompt with fixed context and output limits. Do not select a model size or promise tokens-per-second before those measurements.

## 3. Architecture options and ownership distinctions

| Option | What it provides | Fit for this project |
|---|---|---|
| Train a small language model from scratch | Veronica-origin weights and an end-to-end learning exercise, if data, tokenizer, training, and checkpoints are genuinely created/managed by Veronica. | Recommended for a tiny experiment. On this laptop, expect an educational language-model prototype, not a competitive general-purpose assistant. Training quality is bounded by both compute and clean, representative data. |
| Build a custom tokenizer | A versioned vocabulary/encoding convention controlled by Veronica, including decisions for English, Hindi, and Hinglish/code. | A feasible isolated component, but not a source of reasoning or knowledge. Build/compare it on an approved corpus and freeze its version with each checkpoint. Changing tokenizer later generally requires retraining or carefully verified migration. |
| Pretrain a small model | Teaches next-token prediction from a corpus; it does not automatically teach instruction following, tool use, safety, or factual reliability. | Scale from a tiny reproducible pilot only after a corpus license/provenance policy and held-out evaluation exist. The available laptop is not a credible route to a powerful general-purpose pretrained model. Research on compute-optimal training demonstrates that model size and token count jointly consume substantial compute [1]. |
| Fine-tune an existing pretrained model | Efficiently adapts an existing model; parameter-efficient methods reduce the number of updated parameters [2]. | Useful only as a clearly labeled temporary research baseline if separately approved. Its answers still depend on the pretrained base weights; fine-tuning it does not make Veronica an independent model. Fine-tuning Veronica's own from-scratch checkpoint is compatible with the independence goal. |
| Use an existing model as a temporary baseline | A comparison point for latency, task evaluation, and interaction design. | Optional and approval-gated. It must remain a comparison, not silently become the final answer-generation engine. Record its license, provenance, network policy, and removal criteria. |
| Use a lightweight inference runtime | Executes a compatible model; for example, `llama.cpp` describes itself as LLM inference in C/C++ and supports varied hardware [3]. | A practical future execution layer for compatible Veronica-owned weights. Runtime ownership and model ownership are separate. A runtime may constrain model architecture/format and must be validated on Windows/RTX 3050. It is not itself a model and does not provide training or answer quality. |
| Build a custom inference engine | Control over tokenization/inference internals, kernels, scheduling, and deployment. | A later research goal, not a prerequisite for native answer generation. Building this before a stable model and measured runtime bottleneck would consume effort without creating a capable model. |

**Model-weight ownership** means the model's learned parameters and their provenance are controlled as intended, with the right to use and distribute them; using a pretrained base creates a dependency even if a fine-tune adapter is Veronica's. **Inference-engine ownership** means control of the software that executes weights; it can be independent of who created those weights. **Complete-system ownership** additionally includes tokenizer, data rights and curation, training, retrieval/knowledge, memory, orchestration, evaluation, safety, packaging, and serving. These are separate milestones, not synonyms.

## 4. Recommended modular design

Keep the existing application/provider contracts. Place training/data tooling outside the interactive application runtime so it cannot load datasets or training libraries just to start Veronica. These are conceptual boundaries, not files being created now.

1. **Native model and checkpoint manifest:** a decoder-only causal language model trained from scratch for the first native-generation path. Each checkpoint records architecture/version, parameter count, tokenizer fingerprint, training-data manifest/hash, license/provenance summary, training configuration, metrics, and conversion/quantization history. Checkpoints are local artifacts, never silently downloaded at application startup.
2. **Tokenizer:** train and version a subword tokenizer with deliberate coverage of English, Devanagari Hindi, Latin-script Hinglish, punctuation, and code. Measure fragmentation and round-trip behavior on a held-out multilingual sample. SentencePiece is a relevant tokenizer project/reference [4]; selecting a library is a later compatibility/license decision.
3. **Dataset preparation:** an offline-capable ingestion pipeline with source allowlists, provenance/license records, deduplication, quality filters, language labels, sensitive-data/PII handling, and immutable train/validation/test splits. Exclude private conversation and memory data by default; no user data becomes training material without explicit consent and a retention/deletion policy.
4. **Training pipeline:** separate, reproducible jobs for pretraining and later supervised instruction tuning of Veronica's own checkpoint. Save resumable checkpoints and logs; report loss and held-out metrics. Begin with a tiny corpus and short runs, not a large scrape. Do not use the test set for selecting checkpoints.
5. **Inference boundary:** a future native `AIProvider` implementation owns model loading, tokenizer/runtime pairing, context limits, decoding/sampling, cancellation/timeout, and health checks. It returns the existing provider-neutral response contracts. Initially, the adapter may wrap a compatible lightweight runtime; its output must still come from Veronica-trained weights. Generic `AIService` and `ToolCallingService` should not know which runtime executes the model.
6. **Context and memory:** keep the current bounded conversational context, local SQLite explicit memory, and teaching state as separate data sources. Add a document knowledge store only when retrieval scope, permissions, source provenance, update/deletion, and citation behavior are specified. Do not conflate retrieved facts with model weights or persistent personal memory.
7. **Knowledge/retrieval:** retrieval returns bounded, source-attributed snippets; tool and web results remain evidence. The selected native model reads this evidence and generates the final response. Online retrieval is optional and user/intent-gated; offline mode must not make network calls or claim fresh facts.
8. **Response generation and policy:** the native model generates the final answer. Existing personality, role, memory, and tool orchestration can continue supplying typed context. Add output validation, refusal/safety handling, and multilingual quality tests around the provider, not provider-specific branching in the application.
9. **API/server:** later, expose inference through a versioned local API that shares the same provider contract and supports health, cancellation, bounded request sizes, and explicit model selection. Bind to loopback by default. Remote/cloud exposure requires separate authentication, authorization, TLS, rate/resource limits, audit/privacy policy, and deployment approval; the current project has no server to extend.
10. **Online/offline operation:** local model, tokenizer, memory, and approved local knowledge must work without Internet. Network access for web retrieval, updates, or optional speech is an explicit independent capability. Never route final answer generation to an external LLM in the native mode.
11. **Testing/evaluation:** test provider-contract conformance, deterministic/repeatable load and generation behavior where supported, multilingual tokenization, training-data separation, held-out loss, quality by task/language, retrieval attribution, memory isolation, tool behavior, safety, offline network behavior, latency, peak VRAM, and failure recovery. Compare models on a fixed evaluation set and report measured results separately from estimates.

### Intended request flow

`User text or voice → existing VoiceService/AIService → role, context and explicit memory selection → optional local/web retrieval or registered tool → provider-neutral ChatMessage/tool contracts → factory-selected Veronica native provider → tokenizer + Veronica checkpoint + inference runtime → native model generates the final answer → response/policy checks → AIService → UI or speech output`

In this flow, any external source supplies evidence, not the final answer. During the transition only, Ollama remains available as the existing default. Native mode should be selected only after the native provider passes release gates; its capability metadata must describe what the loaded model actually supports.

### Exit gates before native mode can replace the default

- The loaded checkpoint was trained from scratch or otherwise satisfies the explicitly approved weight-provenance definition; it does not silently depend on an external pretrained answer model.
- Training and evaluation data have approved provenance and privacy rules, with no train/test leakage.
- The tokenizer/checkpoint pair is versioned and verified.
- The native provider passes the neutral contract, tool/vision capability truthfulness, error/health, and offline tests.
- Quality, safety, latency, memory, and reliability meet user-approved thresholds on a fixed evaluation suite. No such thresholds or measured model results exist yet.
- Existing Ollama behavior remains available as a fallback until the user expressly approves changing the default.

## 6. Resource requirements and limitations

| Workload | Compute/storage expectation | Current assessment |
|---|---|---|
| Data curation and tokenizer experiments | Primarily CPU and disk; amount depends on approved corpus and retained versions. | Feasible in principle, but system RAM/free disk are unknown. Tokenizer training does not need the RTX GPU. |
| Tiny model educational training | GPU may accelerate it; VRAM depends heavily on parameter count, sequence length, batch, precision, and optimizer. Dataset/checkpoints require extra disk. | Possible to investigate with a small pilot, not guaranteed before a measured dry run. Expect slow iterations and modest learning value, not assistant-grade answers. |
| Fine-tuning a larger pretrained model | Needs compatible ML packages, model weights, training data, and GPU memory for base weights plus activations/optimizer or parameter-efficient state. | Not in the current dependency set; 6 GB VRAM and Windows make fit/compatibility uncertain. | Local inference | Model weight memory plus runtime, KV cache, context, and OS/display usage. Quantization can reduce weight memory with quality/runtime tradeoffs; exact backend/model support must be verified [5]. | Small models are a reasonable experiment. A 3B FP16 weight file alone is roughly the entire 6 GB VRAM; quantized fit and useful latency remain unverified. |
| Production pretraining or broad model improvement | Large, carefully licensed corpora, sustained compute, checkpoints/backups, evaluation, and repeated experiments. | Not feasible to promise on the known laptop. Consider separate, explicitly approved access to more capable compute only after a measured tiny prototype and a defined budget. |
| Custom inference engine | Engineering time, test hardware, architecture-specific kernels, model-format support, extensive correctness/performance tests. | Not needed to own model weights or generate answers with an existing lightweight runtime. Defer until a measured bottleneck or a deliberate engine-ownership milestone. |

The GPU's reported 6 GB is the only confirmed compute capacity used for sizing here. Actual model fit, tokens per second, training duration, power/thermal behavior, and maximum context length remain unverified. No estimate in this plan should be read as a benchmark.

## 7. Risks and limitations

1. **Capability gap:** a tiny model can be native yet too weak for useful general conversation. “Own weights” does not imply broad knowledge, reasoning, or safety.
2. **Data rights and quality:** training quality and legality depend on licensed, representative data. English-only data would not support the stated Hindi/Hinglish goals; scraped data can contain private or copyrighted material.
3. **Tokenizer/model coupling:** a tokenizer is part of the learned model interface. Changing vocabulary or normalization after pretraining can invalidate token IDs and degrade the checkpoint.
4. **Laptop constraints:** 6 GB VRAM constrains parameter count, sequence length, batch, training states, and concurrency. The unknown CPU/RAM/thermal/storage facts prevent trustworthy schedule and throughput estimates.
5. **Windows/runtime compatibility:** current application tests do not validate CUDA, ML-package wheels, model kernels, or efficient local inference. These need a separate compatibility spike after approval.
6. **Evaluation illusion:** training loss alone does not establish instruction-following, factuality, multilingual quality, or safety. A held-out and task-based evaluation suite is essential.
7. **Knowledge/memory confusion:** user memories, retrieved documents, web evidence, and training examples must remain separate, permissioned, updateable, and clearly labeled.
8. **External service boundaries:** Tavily and online TTS need Internet; they must not be mistaken for native answer generation. Do not send private memory or conversation to external services without a separately approved policy.
9. **Serving and security:** exposing a local or cloud API creates authentication, authorization, abuse, resource exhaustion, privacy, and update risks. No remote service should be exposed by default.
10. **Runtime versus engine ownership:** adopting `llama.cpp` or another runtime may be an excellent way to execute Veronica-owned weights, but does not mean Veronica owns the inference engine. A custom engine adds maintenance and correctness risk without fixing weak weights or inadequate data.

## 9. Decisions requiring approval before implementation

1. **Independence criterion:** must native mode use only weights trained from scratch by Veronica, or may a temporarily pretrained baseline be used for comparison? Recommendation: allow a baseline only as an explicit, non-production, removable experiment; do not make its model the native answer engine.
2. **Model objective:** is the first goal an educational tiny language model, or a useful narrow assistant? Recommendation: approve the tiny educational milestone first and do not promise a useful general assistant from the laptop alone.
3. **Data sources and language priorities:** approve specific licensed corpus sources, data retention rules, and English/Hindi/Hinglish proportions. Decide whether user-generated data is categorically excluded; recommendation: exclude private conversation/memory by default.
4. **Custom tokenizer:** approve a tokenizer-training experiment and criteria for choosing vocabulary/normalization. Recommendation: train only after creating a representative, approved corpus and test suite.
5. **Hardware and budget:** confirm CPU, RAM, free disk, driver/CUDA, thermal conditions, and whether future use of external/cloud compute may be proposed. No external compute is assumed in this plan.
6. **Dependencies and downloads:** authorize a later compatibility investigation and explicitly approve any ML dependency, model/data download, or package changes. None is authorized here.
7. **Inference runtime:** approve the principle that a lightweight external runtime may execute Veronica-owned weights while the model remains Veronica-trained, or require eventual ownership of the engine as well. Recommendation: separate these milestones and defer a custom engine.
8. **API and online operation:** approve local-only API scope first, then separately decide authentication, cloud deployment, web retrieval, external TTS, network access, and handling of user data.
9. **Release gates:** define measurable quality, multilingual, safety, latency, reliability, and resource thresholds before a native provider may replace Ollama as the default.

## Recommendation

Proceed only after approving the decisions above, beginning with dataset governance, evaluation, and a tiny tokenizer/model experiment. Preserve Ollama as the default and fully working provider during learning. Integrate Veronica-trained weights only through the already approved provider-neutral boundary, with external retrieval limited to evidence and the Veronica model generating the final answer. Plan for a long research and engineering journey: this laptop can support learning and small prototypes, but cannot credibly train a powerful general-purpose LLM or prove production readiness by itself.
